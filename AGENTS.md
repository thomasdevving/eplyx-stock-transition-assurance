# Eplyx Lifecycle Impact

This is a standalone Stocklana hackathon repository, separate from the original
Eplyx program-upgrade product.

## Scope

The core model is state + change + consequence model → diff / impact.
ProgramUpgrade retains synthetic differential execution. Phase 2 captures real
token accounts; Phase 3 verifies one Meteora DLMM exposure. Phase 4 applies an
explicit external lifecycle policy to two time views of the same frozen world.
Phase 5 executes one bounded secondary-market exit probe in a fresh local VM
against captured deployed programs and route state. Phase 6 joins the validated
population with independently replayed amount/path/venue matrices and reports
conditional portfolio evidence coverage. Official lifecycle transition
execution remains NotTested. Path-specific execution status must never imply an
official transition, holder signing access or LP/vault exitability. Lifecycle
policies and scenario assumptions must never masquerade as on-chain evidence.

Phase 7 adds deterministic gap selection, bounded read-only capture, real
multi-entity/venue local execution and a versioned coverage delta. Freeze the
plan before capture/execution; never replace unsuccessful selected probes.
Transfer evidence proves token movement only, never secondary-market exit.

Phase 8 resolves exactly one selected entity vertically across five lifecycle
paths. Discovery/policy cannot grant execution proof. OfficialTransition,
Redemption, market exit, Transfer and Withdrawal never inherit each other's
evidence. NotApplicable is entity/context applicability; Unsupported is the
executor/evidence boundary, never proof of non-existence. Preserve the Phase 7
portfolio artifact and semantics; no further horizontal sampling in Phase 8.

Phase 9 deepens only OfficialTransition through bounded public mechanism
reconstruction. Successor mint discovery, source burn, administrative MintTo,
market routes and shared account appearance cannot independently grant official
proof. Unknown eligibility must remain unknown; do not infer issuer/KYC blockers
without mechanism evidence. Never assume issuer signing or private credentials.
Stop after the recorded public search boundary; preserve historical artifacts.

Phase 10 tests one real protocol position through native liquidity withdrawal.
A pool vault never establishes LP ownership. Position pool/owner/range/shares
must be decoded from captured protocol state, with local owner signing explicitly
assumed and key possession unknown. Principal removal, accrued-fee claim,
position closure, market exit and official conversion remain separate facts.
No proof inherits across positions, pools, ranges, fractions, authorities or banks.

Phase 11 evaluates an explicit demonstration assurance policy against existing
pinned evidence only. Ready, Blocked and Incomplete are policy-dependent findings,
never asset safety judgments. Missing/NotTested/mismatched proof is Incomplete;
Blocked requires an exact explicit policy violation. No gate evaluation executes
transactions or performs RPC. Preserve exact path/entity/amount/range/venue/bank/
scenario/digest/signer scope. Principal withdrawal cannot prove fee collection,
closure or conversion; sampled actionability cannot prove population readiness.

Phase 12 normalizes one pinned captured issuer notice entirely offline. Notice
assertions, decoded captured mint identity, explicit demo time and execution
assurance remain distinct provenance classes. Required fields use exact extraction
rules and source locations; unknown conversion ratio/mechanism stay unknown.
Normalized JSON and generated scenarios require fresh source regeneration before
use. Notice wording never grants OfficialTransition proof or readiness. Generated
impact uses the new scenario; frozen path/readiness evidence retains original
hashes under a checked exact economic-policy compatibility bridge. No capture,
HTTP/RPC, new execution, crawler, polling, notice discovery or UI is introduced.

Phase 13 compares deterministic lifecycle times over the same pinned captured world
entirely offline. Counterfactual time changes meaning/relevance, never historical
execution status or proof context. PreEvent is lifecycle-gate applicability, not
Ready. Deadline semantics come only from explicit policy; deadline passage alone
cannot imply Blocked. Holder, vault and position captures remain separate banks;
position inputs are captured pre-execution bytes. Mixed world/policy/proof digests
are non-comparable. No capture, sampling, new execution, valuation, notice ingestion
or UI is introduced.

Phase 14 assesses explicitly submitted structured rollout assertions against the
existing pinned evidence. Candidate acceptance, evidence assessment, assurance
status and local workflow disposition stay distinct. Original policies and execution
classifications remain unchanged; variants declare parent digest and exact changes.
Principal removal never supplies complete exit or conversion. Future target views
are evaluated regardless of observer/PreEvent applicability. Only Accepted + Ready
for the requested exact scope can authorize an inert temporary local marker;
analysis exit 0 cannot authorize it. No new capture, execution, issuer operation,
wallet integration, general rules language or UI replacement is introduced.

Phase 15 uses the existing hero toggle for application-wide consumer/technical presentation and a loopback Node job API around built, allowlisted offline engine commands. Processing success never supplies rollout authorization. All selections preserve exact evidence/policy scope; saved observations and fresh evaluation remain distinct. No wallet, new capture, execution campaign or local marker action is exposed.

On-demand milestone 1 explicitly supersedes Phase 15's fresh-capture restriction: the frontend may request bounded read-only current SPACEX observations through the server-controlled RPC provider. Current-run capture and offline re-decoding never inherit historical execution proof. Preserve the saved demonstration. Multi-asset selection and fresh execution are later milestones; do not claim they are implemented. See docs/on-demand-progress.md.

Keep development focused on this project. Do not restore the old hosted API,
CI bundles, mainnet discovery/acquisition, protocol integrations or website
unless the user explicitly requests them.

## On-demand application milestones

The user-authorized on-demand flow supersedes the earlier UI/acquisition restrictions
for its explicit inspection scope. Milestone 2 adds an imported first-party catalogue
and arbitrary validated Solana mint input through the existing bounded read-only RPC
and offline replay path. Cluster + mint and the exact saved source version remain
pinned per run. Source identity, current account decoding, optional largest-account
sampling and execution evidence are separate. Current runs never inherit saved
SPACEX policy, lifecycle, population or execution facts. Custom issuer association
is unconfirmed; no wallet selection or fresh execution is introduced in milestone 2.

Milestone 3 adds a public owner + selected mint scope using bounded finalized
`getTokenAccountsByOwner` after current mint/program and owner inspection. Version 3
wallet captures replay entirely offline; versions 1/2 remain compatible. Public
balances, confidential unknowns, decoder gaps and provider failures stay distinct.
Focused account selection is browser state only, never execution proof. Current
wallet runs keep lifecycle/readiness null and execution false. No protocol-position
discovery, lifecycle input, signing or fresh execution is introduced in milestone 3.

Milestone 4 adds typed Transfer and bounded Meteora DLMM market-exit checks on
one account discovered in an exact wallet run. Read-only preparation and offline
LiteSVM execution use separate children; the VM receives no RPC credentials.
Only actual execution plus exact reconciliation can create current Proven evidence.
Bind parent/check IDs, wallet/fixture digests, source/mint/amount/recipient or route,
minimum output, captured deployed code, runtime and locally assumed owner signing.
Signing possession stays unknown. Refresh starts untested; historical proof never
supplies current status. Preserve immutable wallet observations and separate check
captures. Missing state is Indeterminate, unsupported configurations are Unsupported,
and Failed requires an actual failed instruction with watched-state rollback.
Transfer requires an explicitly supplied existing recipient token account. Market
discovery scans at most 64 DLMM X-side candidates, selects the lexicographically
first compatible layout and verifies only that selected route, without replacement.
No broadcast, lifecycle input, readiness or Milestone 5 behavior is introduced.

Milestone 5 adds prospective UserProposed replacement-token scenarios bound to one
current wallet run, selected direct account and immutable capture digest. Independently
inspect any supplied replacement mint; existence never establishes issuer relationship,
conversion ratio or mechanism. Reuse consequence classification, path resolution and
exact-scope readiness requirements. Proposed times change lifecycle relevance only;
bytes, balances and current execution classifications stay unchanged. Deadline semantics
remain transition-required without legal/value assertions. Mobility readiness covers
only selected tested amounts/routes; full transition readiness separately requires
OfficialTransition proof. No historical proof, population readiness, future liquidity
prediction, network transaction or wallet signing is introduced. Offline pre-flight
replay regenerates checks through the existing VM; the readiness gate itself never
executes. Refresh starts unverified. See docs/on-demand-progress.md.

Milestone 6 adds an operator-supplied candidate conversion plan, executed against fresh
current production state before rollout. The operator declares a bounded plan — source and
replacement mint, selected account, amount, exact integer ratio, rounding, optional conversion
fee, authority model and proposed reserve — and Eplyx runs exactly one registered repository
mechanism, `Eplyx Demo Candidate Conversion`, in the existing offline VM. The browser supplies
terms only: never program code, a program id, an instruction, account metas, transaction bytes,
a filesystem path, an RPC endpoint or a claimed status. No upload path exists.

The execution bank is freshly captured current state plus an explicitly proposed rollout
overlay; every account carries its origin and proposed accounts never claim captured RPC
evidence. Proven requires the real program to run and every relationship to reconcile exactly:
source debit, burn against the captured mint supply, conversion fee, ratio and rounding,
reserve decrease, replacement credit and the replacement-side transfer fee, all separate.
Token-2022 transfer fees and the candidate conversion fee are never combined.

`ReplacementConversion` and `OfficialTransition` are distinct facts in distinct status slots.
An OperatorSupplied plan can make `ReplacementConversion = Proven` and `CandidatePlanReadiness
= Ready`; it can never make `OfficialTransition` anything but `NotTested`, and full transition
readiness stays Incomplete without independent issuer binding. Transfer, market exit, a DEX
swap into the replacement token, successor-mint existence and an unrelated burn plus MintTo
never satisfy conversion. The candidate authority is a program-derived address assumed locally
and cannot establish issuer identity or control; no issuer key is ever assumed. Refresh starts
untested and no proof crosses runs, accounts, amounts, plans, program builds or banks.
See docs/on-demand-milestone-6-conversion.md.

Milestone 8 introduces strict operator transition packages through the registered
fixed-ratio conversion adapter. A package supplies candidate SBF bytes and exact
terms/config, never instructions, account metas, RPC endpoints or claimed proof.
Fresh current capture, exact local conversion and Milestone 7 stress execution
remain separate from issuer binding. Package, program, config, captured banks,
frozen selection and VM results are rechecked on offline replay. OfficialTransition
stays NotTested. See docs/on-demand-milestone-8-package.md.

Milestone 9 adds a deployment gate over the existing verified package report.
Block-only permits Incomplete with warnings; strict blocks it. Neither policy
changes analytical findings or grants execution, population or issuer proof.
The exact packaged candidate bytes must be the only candidate bytes loaded into
LiteSVM. Saved Milestone 8 reports retain their original replay semantics.
See docs/on-demand-milestone-9-ci-gate.md.

Milestone 10 adds a frozen bounded second-layer authority-resolution plan over the
fresh population's already captured recorded-authority accounts. Coarse classes,
control resolution and conversion outcomes remain separate. Exact DLMM pool/vault
PDA proof establishes protocol custody only; SPL multisig decoding cannot supply
private approvals. No non-wallet account gains a wallet signer or conversion proof
from resolution. Historical package replay remains unchanged; fresh stress worlds
bind the authority plan. See docs/on-demand-milestone-10-authority.md.

Milestone 11 adds a bounded coherent final execution recapture after discovery
and frozen selection. The exact final account set and Clock/context rule are
reverified offline before candidate VM execution; at most three serial final
attempts use a monotonic minContextSlot chain. Source drift or failed coherence
is Indeterminate and never triggers peer replacement, amount adjustment or
approximate-bank execution. Static code identity and proposed overlay inputs
remain separately bound. Historical schema 1 reports keep original replay
semantics. See docs/on-demand-milestone-11-coherence.md.

## Architecture

- engine/src/scenario.rs separates the change from state inputs.
- engine/src/types.rs and executor.rs carry state and execution primitives.
- diff.rs compares observable results.
- lifecycle/policy.rs describes generic external lifecycle specifications.
- lifecycle/consequence.rs evaluates immutable snapshots entirely offline,
  with separate entity and protocol observations and no invented valuation.
- probe/ contains generic path/status/assessment models and a bounded DLMM
  adapter. Capture is read-only; replay is offline through the existing LiteSVM
  backend. Never submit mainnet transactions or substitute quotes for execution.
- coverage/ joins validated Phase 4 state with fresh offline Phase 5 execution.
  Representative classes never inherit execution evidence. Use maxima across
  independent amounts/venues/paths, not summed pool capacity. Public-balance
  context mismatches receive no earlier-population amount coverage. Unsupported
  means adapter/signing capability limits, never proof that the asset cannot exit.
- money.rs provides integer fixed-point values.
- expansion/ keeps observed gaps, eligibility, decomposed marginal scores,
  immutable selected plans, content-addressed measured results and exact deltas
  separate. Public updates verify hashes and fresh offline execution. Current
  finalized captures are never described as historical validator banks.
- resolution/ provides the generic six-status lifecycle path matrix, with an
  adapter that hash-checks Phase 7 artifacts and fresh-replays only the requested
  entity. Stock/issuer facts live in discovery data and frozen evidence, never
  resolver conditionals. Assumed local signing remains distinct from possession.
- transition/ separates issuer communications, decoded current successor state,
  observed transaction/program/account patterns and exact official mechanism
  identity. Its frozen-evidence investigation is offline; no official execution
  adapter is established by the current production result. A bounded search
  cannot establish transition non-existence.
- position/ models one generic protocol-position shape and exact withdrawal
  scope; the bounded Meteora PositionV2 adapter re-derives exposure/authority,
  executes deployed RemoveLiquidityByRange2 in the existing fresh VM, and
  reconciles raw token, withheld-fee, bin-supply and position-share deltas.
  Stored claims alone never construct verified withdrawal evidence. Discovery
  and replay use frozen public evidence; this phase adds no global LP index.
- readiness/ keeps assurance requirements separate from economic lifecycle policy.
  Its frozen-evidence adapter verifies declared digests and published measurement
  bindings without VM replay. Generic findings enforce scope isolation; the demo
  policy is data, not an issuer rule. Entity and population gates stay separate.
- counterfactual/ owns one validated immutable captured world, reuses the lifecycle
  evaluator at explicit deterministic time boundaries and compares classifications,
  path relevance and lifecycle-gate applicability. Published exact readiness findings
  and original path contexts remain unchanged; shared entity indices avoid duplicated
  population identities. Internal evaluator reuse skips redundant snapshot validation
  only under immutable ownership after pinned canonical input verification.
- rollout/ normalizes bounded structured candidate claims, borrows immutable verified
  readiness evidence, checks exact cited facts and reuses existing requirement/policy
  evaluation. Explicit policy variants and a non-deserializable assessment preserve
  scope isolation. The guard consumes typed readiness status and completion codes
  and can only create a temporary inert marker.
- notice/ supplies generic captured-source/event/provenance/scenario models,
  one deterministic issuer adapter, and offline orchestration of existing impact
  and frozen path/readiness evaluation. Successor identity is an additive fact;
  it never supplies conversion mechanics. Assurance policy remains unchanged.
- conversion/ models operator-supplied candidate conversion plans and executes exactly one
  registered repository mechanism through the existing LiteSVM backend. The plan model is
  bounded and serializable: no DSL, no scripts, no supplied account metas or transaction bytes.
  Provenance is explicit and only OperatorSupplied has an executable adapter. Observed captured
  accounts and the deterministically derived proposed overlay never mix, and the candidate
  program is never described as deployed. VerifiedReplacementConversion has no deserialization
  constructor: only a validated plan, actual VM execution and exact reconciliation build one.
  A proven candidate plan is evidence about that plan under its declared authority model, never
  an issuer-defined official transition.
- programs/eplyx-demo-conversion/ is the registered candidate mechanism. It enforces the ratio,
  rounding and conversion fee itself in checked integer arithmetic and performs real token
  CPIs, so host-side calculation can never stand in for execution. It is not deployed anywhere.
- corpus.rs, interpret.rs, impact.rs, cluster.rs, shrink.rs and report.rs retain
  synthetic lending regression/demo behavior, not lifecycle domain semantics.
- interface/ and programs/fixture-lending/ are the synthetic harness only.

No path dependency may point outside this repository. The sole working branch
is main. Phase-specific scope and evidence limits are documented in docs/.

## Validation

make test generates fixture states, builds synthetic SBF programs and runs the
relevant unit and integration tests. Also run make fmt-check and make lint.
Missing program artefacts remain failures; never silently skip execution tests.
Report checks as pending until they have actually been executed.
