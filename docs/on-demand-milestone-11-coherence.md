# Milestone 11: coherent current-state execution capture

The fresh Solami SPACEX run from Milestone 10 exposed a real capture boundary: the final `getMultipleAccounts` response had finalized context slot 449525292, while the Clock account bytes inside it encoded slot 449525294. The previous executor correctly refused that bank. A nearby slot is never accepted as equivalent, and Clock bytes are never rewritten to make a local VM run succeed.

## Capture contract

Wallet inspection and population enumeration discover candidates. The stress plan freezes the exact selected accounts and amounts before case capture. For each selected case, and for the standalone candidate conversion check, the server derives the full final account list from the validated plan and inspected program headers. It then issues at most three serial finalized `getMultipleAccounts` requests for that **same list**. The first request uses the highest prerequisite context; after a Clock/context mismatch the next `minContextSlot` is strictly above both observed slots. The timeout is 90 seconds for the final capture phase, and the bounded execution RPC client has one transport attempt per recorded call. The browser controls neither limit.

Replay reconstructs the request chain from saved RPC records. It requires every response context to satisfy its lower bound, the final Clock bytes to encode exactly the final response context slot, unchanged non-Clock account values across final attempts, and no extra attempt after success. A missing or incompatible final batch yields `CouldNotEstablishCoherentExecutionContext` and `Indeterminate`, with no VM execution and no conversion proof. There is no slot tolerance. Captures with a provider error also remain `Indeterminate`; the error is never an executed failure.

The verified execution context lists the discovery response contexts, exact final account addresses, runtime owners, lamports, executable flags, data SHA-256 hashes, Clock data hash and slot, response contexts and `minContextSlot` chain. `atomic_single_slot` is **false**: this contract verifies a coherent final execution capture under an explicit RPC rule; it does not claim an atomic validator snapshot across wallet, population and execution observations. The final account batch supplies the observed LiteSVM bank. Earlier wallet and population bytes are discovery-only and cannot supply missing final bank accounts. Candidate config, reserve and program bytes are proposed overlay inputs derived from the exact plan and validated artifact digest. Deployed program headers and ProgramData are final-batch code identities with canonical loader links and deployment checks.

The final source account is compared with its wallet or population observation across data bytes, runtime owner, executable flag and lamports. A change gives `SourceStateChanged` while preserving the frozen amount and selected case. Source and replacement mint accounts are also compared with their earlier inspections for new captures. Program/header/ProgramData changes during recapture invalidate the bank. The candidate config and reserve are regenerated from the same immutable plan; they never become purported RPC state. Clock remains VM input because the deployed Token-2022 program can use its epoch for transfer-fee behavior, even though the candidate program does not read Clock directly. The VM always receives the captured Clock bytes and the exact packaged candidate ELF.

Current captures and stress bundles use schema 2. Saved schema 1 Milestone 8/9/10 captures keep their original replay semantics and report bytes; they gain no retrospective coherence claim. Both standalone conversion and package/stress execution use the same `conversion::coherence` module and existing LiteSVM/reconciliation path. Failed capture cannot become `Failed` conversion or `Blocked` analytical readiness. The Milestone 9 block-only/strict policy mapping is unchanged. OfficialTransition remains NotTested and no mainnet transaction is sent.

## Live FastRPC acceptance and provider boundary, 23 September 2026

The final read-only FastRPC SPACEX run enumerated 17,852 token accounts, including 10,046 positive public balances. Its 11-account final candidate batch returned at context slot 449691835 with Clock bytes encoding the same slot. One attempt established the explicit coherence rule. The proposed candidate conversion executed in the local VM, reconciled and was `Proven` for that exact plan. The second asset independently enumerated 64,806 token accounts, including 33,910 positive balances, and its 11-account batch passed the same rule at slot 449692039. Its proposed candidate conversion also reconciled. Both final reports expose the four discovery response contexts, final account identities and hashes, retry chain and fixture digest, and replay offline with exit 0. These are local candidate results under assumed signing; neither establishes issuer authorization or OfficialTransition.

FastRPC rejected the separate 100-address recorded-authority inspection with `-32602` in both final runs. Authority resolution was `NotPerformed`, no live stress case was selected, both stress and population rollout readiness stayed `Incomplete`, and block-only remained WARN. The same SPACEX evidence under strict policy was BLOCK. The complete second-asset population is a new FastRPC observation; it does not retroactively make Solami's two different-slot diagnostic pages one frozen population.

An earlier FastRPC SPACEX capture completed population enumeration but its 11-account final request failed with `-32602`. A sanitized diagnostic at that time said “Too many inputs provided; max 5”. The raw capture was replayed with the final binary and its report regenerated **offline** in a separate directory. It remains `Indeterminate` with `CouldNotEstablishCoherentExecutionContext`, no VM execution and no historical substitution. The later successful 11-account requests show that provider behavior varied across these observations; neither result is rewritten or generalized to the other. Exact capture times, directories, hashes and statuses are in [`reports/milestone11-validation.json`](../reports/milestone11-validation.json).

Offline tests cover later and earlier Clock mismatches, a successful monotonic retry, bounded exhaustion, source and program drift, exact frozen-case retention, proposed config terms and refusal to trust serialized coherence flags. Seven executable mutations were killed by named assertions. After the final executable change, the full workspace, program, fmt, Clippy, Node and frontend checks passed; historical Milestone 8/9/10 package replay retained its prior bytes and exit semantics. No network transaction was sent.
